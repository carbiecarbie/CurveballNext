# Controlled qualification (test only)

These tools are excluded from production frontend/backend builds. A source harness is not acceptance evidence. The fixed manifest has eight variants × two defenders × 300 opportunities = 4,800. Keep 100 basic, 100 curved/diagonal/wall and 100 late cases per cell, all 50/100/200/400 ms margins and 60/120/144 Hz strata. Seeds/order and independently predicted incoming targets are fixed before execution. Do not replace a rejected/borderline opportunity.

Build with `node tools/m5/build-qualification.mjs`. `node dist-server/qualify-local.mjs 60` measures ten rooms and twenty serialized in-process clients, including a visibly blurred controller. It measures local CPU/JSON/queues, not TCP, Fly CPU quota or fairness. Supported duration is 10..7200 seconds; retain the actual duration and final counts. Output is ignored under `captures-local/m5-local/`.

Capacity schema `curveball-online-local-capacity-2` separates executed batches from idle polls. An executed batch is one `Authority.pump` invocation that executes at least one room simulation tick, measured from immediately before to immediately after that call. It includes queued command processing, simulation, serialization and synchronous in-process delivery; client pumping outside that call is excluded. Each invocation counts once, including catch-up batches, with its room-tick count retained. An idle poll executes zero room ticks and contributes only to poll/idle/payload observation counts. Scheduler lateness is a separate population: pump start minus the pending nominal boundary on every due scheduled wake. No warmup is discarded; setup precedes the timed run, and all timed-run observations are reported, not a rolling window.

`executedBatchP99Ms` and `latenessP99Ms` use nearest rank: sort ascending and select index `ceil(0.99*N)-1`; empty populations return `null`. The saved JSON includes run-wide raw executed durations, corresponding room-tick counts, and scheduled-wake lateness, plus each population's count and definitions. Independently sort these raw arrays to recalculate the percentiles. Thus 980 executed batches at 1 ms plus 20 at 25 ms yield p99=25 ms irrespective of 5,000 idle polls. Console output omits raw arrays; retain the saved file. Payload maximum is updated incrementally, with no payload array or function-argument expansion. Idle polls store no samples; a two-hour 30 Hz run retains approximately 216,000 entries per executed/scheduled population (three numeric arrays, about 5.2 MB of numeric contents plus array/serialization overhead). Large-population tests cover 225,000 and 720,000 observations without an hour-long run. This runner does not change the server's bounded, separately labeled rolling health metrics.

Schema-1 reports are historical. Their `batchP99Ms` mixed idle polls with execution and cannot establish executed-batch performance or be reliably corrected without raw samples. Their raw batch/lateness populations were not retained; do not manufacture revised historical percentiles. In particular the retained scheduler-lateness p99=15.4612 ms failure against the unchanged 10 ms target remains a failure. Correct calculation and successful report generation do not qualify performance, production capacity or fairness.

Browser DOM samples use their actual event capture time, normalized from performance-relative or legacy epoch timestamps into the client's `performance.now()` domain. Non-finite, negative, future or ambiguous origins are discarded without handler-time fallback. Equality with Rally activation/control enablement is conservatively rejected. Diagnostics retain capture `at` and `handledAt` separately; wire send remains a separate record. These client timestamps never authorize collision timing or rewind.

The capture page schedules the declared 60/120/144 Hz draw strata and records actual intervals. It **does not emulate a 120/144 Hz display on 60 Hz hardware**. Scheduling, image capture and cadence validation remain unqualified on suitable hardware. `inputRecords` distinguishes actual capture from wire send; presentation `sendTime` is only controller queue time. Do not report a recorded sequence as a pass.

Packet-loss gates require a Linux TCP shaper. Application-level drops cannot represent TCP retransmission. Use three isolated receiver environments (server, A, B) with routable addresses, and apply `ingress-netem.sh` to the receiver interface for each direction. The first two values per player in `profiles` are upstream base/jitter, next two downstream, last loss %. For C3 use 40/10 ms and 1% in each direction. C5a uses A upstream 70/10 and downstream 10/10, B the reverse. Use independent predeclared seeds on all four paths. Every direction is capped at 1 Mbit/s. Pass the appropriate source peer IP and server TCP port; upstream runs on the server receiver, downstream on each client receiver. Preserve SYN/ACK/data retransmissions too. Retain `tc -s qdisc`, kernel/iproute versions, configuration hash and full redacted packet/arrival traces; verify shaping actually reached the intended paths. Uniform jitter is bounded propagation delay; loss stalls/outliers remain in evidence. Netem's seed does not guarantee identical cross-kernel packet schedules; retain actual traces and repeated outcomes.

If proxies forward browser TCP to the shaped environment, retain both legs and prove the shaping precedes receive/delivery. Supply their loopback WS URLs as `?wsA=...&wsB=...`. Production WSS/TLS and deployed routes require separate verification. Do not silently treat an unshaped WS run as that gate.
